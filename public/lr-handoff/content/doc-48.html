Detailed Findings

CS-001: Incorrect Discount Parameters Check (Medium)

Source: ChainSecurity (CS-CURVE-PT-ORACLE-001)

Description: In _update_discount_params(), the check to ensure discount <= DISCOUNT_PRECISION uses self.slope and self.intercept (the old values) instead of the proposed _slope and _intercept values. This allows a malicious or careless Manager to set new discount parameters that would cause _calculate_price() to revert due to underflow when computing DISCOUNT_PRECISION - discount, effectively making the oracle unusable.

Affected Lines: PtOracle.vy:243-247

Recommendation: Validate the proposed values (_slope, _intercept), not the stored ones. Recompute time_to_maturity_years from the current state and compute new_discount using _slope and _intercept, then assert new_discount < DISCOUNT_PRECISION before updating storage.

SM-HIGH-01: Incorrect _update_discount_params validation (High)

Source: StateMind AI

Description: Same issue as CS-001. _update_discount_params validates using the current self.slope/self.intercept instead of the proposed _slope/_intercept, so unsafe new values can be accepted, and later cause reverts when used at runtime.

Impact: Protocol-wide DoS: If discount > DISCOUNT_PRECISION, discount_factor underflows and reverts under checked arithmetic, breaking price() and price_w() across the system.

Affected Lines: PtOracle.vy:243-247

Recommendation:

  • Enforce the invariant 0 <= discount < DISCOUNT_PRECISION end-to-end and document it

  • Validate the proposed values, not the stored ones

  • Recompute time_to_maturity_years from the current state and compute new_discount using _slope and _intercept

  • Assert new_discount < DISCOUNT_PRECISION before updating storage

  • Include clear revert messages

  • Optionally cap acceptable discounts further (e.g., <= 95% of DISCOUNT_PRECISION) to reduce risk from extreme settings

SM-MEDIUM-01: MEV Exploitation via Immediate Parameter Updates (Medium)

Source: StateMind AI

Description: PtOracle's pricing parameters are updated via set_linear_discount set_slope_from_apy And take effect immediately. The update gating uses a strict inequality check block.timestamp > last_discount_update + min_update_interval. Because min_update_interval can be configured to 0, and there is no timelock or commit-reveal. Updates can be executed as frequently as once per block/second and applied atomically.

MEV Exposure: Bots can monitor the mempool for parameter-update transactions, front-run trades at the old price, let the update execute, and then back-run at the new price to capture the discrete price jump.

Impact:

  • MEV/sandwich risk: Attackers can front-run on old parameters and back-run on new parameters to arbitrage the discrete price change

  • Volatility and coordination risk: Managers can rapidly flip parameters (especially with min_update_interval = 0)

  • Reputational and financial impact from predictable, profitable MEV opportunities

Affected Lines: PtOracle.vy:262-270, 274-305, 318-320

Recommendation:

  1. Add delay/commit mechanisms: implement a two-step commit-reveal scheme or a timelock

  2. Enforce sensible lower bounds and cooldowns: set a non-zero minimum for min_update_interval, add per-parameter cooldowns, cap maximum change per interval

  3. Correct the rate-limit predicate: change to >= so effective interval matches configured value, OR document the current strict behavior and rename variable (e.g., min_seconds_before_next_update)

  4. Reduce discrete jumps: introduce gradual/ramped transitions so parameter changes phase in over time

  5. Execution privacy: use private transaction channels (e.g., Flashbots) when executing updates

SM-INFO-04: Misleading "0 = no limit" Comment (Informational)

Source: StateMind AI

Description: The comment on max_slope_change and max_intercept_change says "0 = no limit", but the implementation uses change <= limit and the constructor initializes both limits to max_value(uint256) as the real "no limit" sentinel. With this logic, a limit of 0 actually forbids any non-zero change (hard freeze), while max_value(uint256) behaves as unbounded.

Impact: Admins following the comment may set a limit to 0, expecting "no limit", but instead freeze discount updates until limits are raised again. This is a misconfiguration/UX risk causing temporary DoS of parameter updates.

Affected Lines: PtOracle.vy:45-49, 124-129, 219-235

Recommendation: Update comments to match behavior (e.g., max_uint = no limit; 0 = no change allowed) and/or adjust the code so that 0 truly means "no limit" by skipping the check when the limit is 0. Add tests and docs that explicitly cover 0, bounded values, and max_value(uint256) semantics.

CS-002: Code Duplication (Informational)

Source: ChainSecurity (CS-CURVE-PT-ORACLE-002)

Description: _update_discount_params() and _calculate_price() both contain the same logic to compute the discount, which is currently duplicated. This logic could be refactored into a separate internal function to reduce code duplication and improve maintainability.

CS-003: Gas Savings (Informational)

Source: ChainSecurity (CS-CURVE-PT-ORACLE-003)

Description: The following gas optimizations were identified:

  1. pt could be made immutable, as it is set only once in the constructor

  2. underlying_oracle could be made immutable, as it is set only once in the constructor

  3. In __init__(), when logging PriceUpdated, the storage load of self.last_price could be avoided as the value was stored just before

  4. In _update_discount_params, self.slope and self.intercept are loaded from storage multiple times. Caching them in local variables would save gas.

CS-004: Incorrect Comments (Informational)

Source: ChainSecurity (CS-CURVE-PT-ORACLE-004)

Description:

  1. The comment "0 = no limit" for max_slope_change and max_intercept_change is incorrect - 0 actually prevents any change (covered by SM-INFO-04)

  2. The comment "Rate limiting for set_linear_discount" on last_discount_update is misleading as this variable is also used in set_slope_from_apy()

Items Requiring Research & Response

CS-009: Out-of-Date Price in price_w Function

Source: ChainSecurity (CS-CURVE-PT-ORACLE-009) Priority: MEDIUM

Description: While price() always returns up-to-date prices with respect to the underlying price oracle, price_w() might return a cached price if:

  • Expiry has not been reached yet

  • The last call to price_w() was in the same block as the current call

In such a case, the function returns self.last_price. This could be problematic if the underlying price oracle can have multiple updates in the same block, as the PT oracle would not reflect the latest of those updates.

Research Questions:

  • What underlying oracles will be used? (Chainlink, custom, etc.)

  • Can those oracles update multiple times within a single block?

  • How does LlamaLend call price_w() ? Could same-block staleness cause issues?

  • Are the gas savings from caching worth the potential staleness?

Possible Outcomes:

  • Accept: Document the behavior clearly for integrators

  • Fix: Remove same-block caching or add parameter version tracking

CS-008: Stale last_price After Expiry

Source: ChainSecurity (CS-CURVE-PT-ORACLE-008) Priority: MEDIUM

Description: After the PT expiry, the price returned by price_w() is no longer stored in last_price. Integrators relying on the stored price may be affected if they do not switch to calling the view function price() instead.

Research Questions:

  • Are there any integrators (including LlamaLend) that read last_price directly instead of calling price() or price_w()?

  • Should last_price Should the price be updated to the underlying price after expiry for consistency?

  • Is there a reason NOT to update last_price after expiry (gas savings)?

Possible Outcomes:

  • Accept: Document that last_price is not updated post-expiry

  • Fix: Update last_price in price_w() even after expiry

CS-NOTE-8.1: Usage of Oracle in Curve LlamaLend Markets

Source: ChainSecurity (Note 8.1) Priority: HIGH

Description: This oracle is intended to be used as a collateral price oracle for Curve LlamaLend markets. By design, the price of this oracle does not reflect the actual market price of the PT token, but rather an estimate based on a linear function. This design choice carries non-trivial economic implications when used in a Curve LlamaLend AMM, as it can lead to situations where the oracle price diverges significantly from the market price, potentially causing unexpected liquidations or missed trading opportunities.

Research Questions:

  • What is the maximum acceptable divergence between the oracle price and the PT market price?

  • How will borrowers be protected from liquidation when the market price drops but the oracle price remains higher?

  • Conversely, how will the protocol be protected when the oracle price is lower than the market price (undercollateralization risk)?

  • Should there be circuit breakers or monitoring for extreme divergence?

  • What documentation is needed for LlamaLend users to understand this risk?

Deliverables:

  1. Risk analysis document outlining divergence scenarios

  2. Recommended parameter ranges for slope/intercept to minimize divergence

  3. User-facing documentation explaining the pricing model and risks

Open Questions (ChainSecurity)

Design Decision: set_linear_discount vs set_slope_from_apy

Both functions set discount parameters, but have different behaviors:

  1. Why are both needed? The intercept and slope can be easily calculated off-chain from the APY, or vice versa.

  2. Why does one function allow setting the intercept and the other always set it to 0?

  3. What are the practical scenarios where the intercept must be set to non-zero values?

Task 1: Fix Discount Parameter Validation Bug

Reference: CS-CURVE-PT-ORACLE-001

Priority: HIGH

Assignee: @Zeki

Description: The _update_discount_params() function at lines 243-247 currently validates the discount using the old stored values (self.slope, self.intercept) instead of the proposed new values (_slope, _intercept). This allows a Manager to set parameters that would cause _calculate_price() to revert due to underflow when computing DISCOUNT_PRECISION - discount.

Required Changes:

  1. Modify the validation logic in _update_discount_params() to compute the discount using the proposed _slope and _intercept parameters

  2. Recompute time_to_maturity_years from current block.timestamp and pt_expiry

  3. Calculate new_discount = (_slope * time_to_maturity_years) // DISCOUNT_PRECISION + _intercept

  4. Assert new_discount <= DISCOUNT_PRECISION before updating storage

  5. Add a clear revert message: "new discount exceeds precision"

Task 2: Fix Incorrect Comments

Reference: CS-CURVE-PT-ORACLE-004

Priority: LOW

Assignee: @Zeki

Description: Multiple comments in the codebase are inaccurate or misleading:

  1. The comment on lines 45-49 states "0 = no limit" for max_slope_change and max_intercept_change, but the actual behavior is the opposite. The implementation uses change <= limit comparison, and the constructor initializes both to max_value(uint256) the true "no limit" sentinel. Setting a limit to 0 actually freezes all parameter changes.

  2. The comment "Rate limiting for set_linear_discount." last_discount_update is misleading, as this variable is also used in set_slope_from_apy().

Required Changes:

  1. Update comment on lines 45-49 to accurately describe behavior: # max_value(uint256) = no limit; 0 = no changes allowed (freeze)

  2. Change line 56 comment from # Rate limiting for set_linear_discount to # Rate limiting for discount parameter updates (used by set_linear_discount and set_slope_from_apy)

  3. Add inline documentation explaining the limit semantics clearly

  4. Consider whether to change the logic so 0 truly means "no limit" by adding a conditional skip: if self.max_slope_change != 0: assert slope_change <= self.max_slope_change

  5. Review all other comments for accuracy

Task 4: Add Tests for Parameter Limit Edge Cases

Reference: CS-CURVE-PT-ORACLE-004

Priority: MEDIUM

Assignee: @Zeki

Description: Current tests do not comprehensively cover the edge cases for max_slope_change and max_intercept_change limit behavior.

Required Tests:

  1. Test that setting the limit to 0 prevents ANY non-zero change (freeze behavior)

  2. Test that setting the limit to max_value(uint256) allows unlimited changes

  3. Test boundary conditions: change exactly equal to limit (should pass), change exceeding limit by 1 (should fail)

  4. Test the interaction between slope and intercept limits when both are constrained

  5. Add test documentation explaining the expected semantics

Task 5: Refactor Duplicate Discount Calculation Logic

Reference: CS-CURVE-PT-ORACLE-002

Priority: LOW

Assignee: @Erdal @Zeki

Description: The discount calculation logic is duplicated in two places: _update_discount_params() (lines 236-247) and _calculate_price() (lines 166-173). This violates the DRY principle and increases maintenance burden.

Required Changes:

  1. Create a new internal view function _calculate_discount(slope: uint256, intercept: uint256) -> uint256

  2. Move the shared logic: time-to-maturity calculation and discount formula

  3. Update _calculate_price() to call _calculate_discount(self.slope, self.intercept)

  4. Update _update_discount_params() to call _calculate_discount(_slope, _intercept) for validation

  5. Ensure gas impact is acceptable (should be minimal due to inlining)

Task 6: Apply Gas Optimizations

Reference: CS-CURVE-PT-ORACLE-003

Priority: LOW

Assignee: @Erdal

Required Changes:
